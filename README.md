# docindex

Index PDF and DOCX files and search them in plain language.

Each file goes through four steps: its text is extracted and cleaned, split
into chunks, embedded with Gemini (`gemini-embedding-001`), and stored in
PostgreSQL with pgvector. A search returns the 5 closest chunks.

## 1. Installation

You need Python 3.14 and Docker.

```bash
python -m venv .venv
source .venv/bin/activate        # PowerShell: .venv\Scripts\Activate.ps1
pip install -r requirements.txt
docker compose up -d
cp .env.example .env             # then add your Gemini key
```

The database listens on port **5433**, not 5432. This avoids a clash with a
local PostgreSQL install. The first run creates the table automatically.

## 2. Environment variables

The scripts need two variables, both set in `.env`:

- `GEMINI_API_KEY`: your Gemini API key (the free tier works).
- `POSTGRES_URL`: `postgresql://postgres:postgres@localhost:5433/docindex`

A variable already set in the shell overrides `.env`. Neither value is ever
printed.

## 3. Usage

```bash
python index_documents.py --file samples/urban_beekeeping.pdf --strategy paragraph
python search.py --query "how do I stop bees swarming"
```

Choose one of three split strategies:

- `fixed`: chunks of up to 1,000 characters, each overlapping the previous one
  by up to 200 characters.
- `sentence`: whole sentences, packed into chunks of up to 1,000 characters.
- `paragraph`: one chunk per paragraph. Only a paragraph longer than 1,000
  characters is split.

Indexing the same file with the same strategy again replaces its earlier
chunks. Add `--verbose` to see debug logs and tracebacks.

## 4. Design decisions

**How is the code organised?**
The services depend only on four interfaces: extractor, chunker, embedder and
repository. The concrete classes are created in one place,
`docindex/bootstrap.py`, so the tests can swap in a fake Gemini and a fake
database. The two scripts are 3 lines each.

**How is the text cleaned?**
One shared `TextCleaner` handles both PDF and DOCX text. It:

- normalises Unicode;
- drops page numbers;
- joins wrapped lines;
- rejoins hyphenated words (`pro-` + `ductivity` → `productivity`).

Paragraphs come out separated by a blank line, and every chunker relies on
that. pypdf runs in layout mode, because the plain mode loses the gaps between
paragraphs.

**Why count characters, not tokens?**
Gemini has no local tokenizer, and counting tokens through the API costs one
call per chunk. 1,000 characters is about 250 tokens, far below the model's
2,048-token limit.

**Why check the database before calling Gemini?**
A stopped database then fails in seconds and costs no API quota. All chunks are
embedded before anything is written. Replacing chunks happens in one
transaction, so a failed run never loses the old chunks.

**How are errors handled?**
Every failure prints one `Error: ...` line and exits with a fixed code:

| Code | Meaning |
|---|---|
| 0 | success, including "no results" |
| 1 | unexpected error |
| 2 | bad arguments or missing config |
| 3 | bad document |
| 4 | Gemini failure |
| 5 | database failure |

**What about rate limits?**
The Gemini SDK's built-in retry is turned on. It makes up to 8 attempts, with
backoff of up to 60 s on 429 and 5xx errors. Its total wait of over 2 minutes
outlasts a free-tier per-minute quota window.

**How are secrets protected?**
Error messages are our own text and never include library output. Logs show
only the database host and name. A test runs every outcome with `--verbose` and
checks that the key and password never appear.

**What problems came up while building it?**

- An invalid Gemini key returns HTTP 400, not 401. Mapping the status code
  alone would have hidden the real cause.
- "Corrupt file" and "file has no text" need different fixes, so they are
  separate errors.
- On Windows, Docker silently swallows connections to a stopped container. A
  3 s connect timeout keeps the run from hanging.
- Library warnings (pypdf, psycopg) broke the one-error-line rule, so they are
  silenced unless `--verbose` is on.
- Windows console output crashed on the `ﬁ` ligature, so output is forced to
  UTF-8.

## 5. Sample documents

The files in `samples/` are generated by `python samples/generate_samples.py`
(that needs `requirements-dev.txt`):

- `urban_beekeeping.pdf`: paragraphs, a hyphenated word, page numbers and a
  page break.
- `remote_work_policy.docx`: a heading, a table and a footer (both must be
  skipped), and a ligature.
- `scanned_no_text.pdf`: an image with no text layer.
- `empty.docx`: an empty document.

To set the key for one command in PowerShell, run
`$env:GEMINI_API_KEY='invalid'`, then your command, then
`Remove-Item Env:GEMINI_API_KEY`.

When the database is stopped, every command prints `Error: Cannot connect to
PostgreSQL: check POSTGRES_URL in .env and that the database is running` and
exits with 5.

## 7. Assumptions & limitations

- The SQL and the real Gemini calls are tested by hand, not by the automated
  tests.
- PDF paragraphs are detected from the vertical gaps between them, so
  multi-column layouts and indent-only paragraphs are not handled. A paragraph
  that crosses a page break becomes two.
- There is no OCR. DOCX tables, headers and footers are not indexed.
- The file type comes from the extension only.
- Sentence detection is English only. A very long sentence can be cut
  mid-sentence.
- Search always returns up to 5 results, even when none of them are relevant.
  It shows no score and covers all strategies.
- Two files with the same name in different folders overwrite each other's
  rows.
- On the free tier, large documents can be slow or can use up the daily quota.

## 8. Running tests

```bash
pip install -r requirements-dev.txt
python -m pytest     # no network or database needed, a few seconds
python -m mypy
```

The tests run the real extraction and chunking code on `samples/`. Gemini and
the database are replaced by fakes.
